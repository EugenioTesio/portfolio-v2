Un skid de lubricación en una planta y un cargador en una playa de estacionamiento no fallan como una app móvil. Fallan como física: ruido de modo común en un par largo, un transceptor que se traba, un corte de turno noche que dura más que la RAM. Si la nube nunca ve el paquete, la facturación está mal, una máquina se queda seca o una sesión nunca cierra.

Este artículo es una guía de campo para el camino desde serial diferencial y OCPP 1.6 hasta una API de ingestión en la nube — sin pretender que un tutorial de MQTT es un sistema industrial. Los nodos de edge son publicadores poco fiables. El bus es un entorno analógico hostil. El backend es un ledger idempotente, no una manguera de copos de nieve únicos. Esa distinción explica la mayoría de los compromisos que siguen.

Qué no es esto. No es un esquemático para una estación meteorológica hobby con ESP32. Si tu enlace es USB en un banco de laboratorio y tu “backend” es un archivo JSON, un script bien delimitado sale más barato. Esta arquitectura existe porque EMI, brownouts y tormentas simultáneas de reconexión son el default, no el incidente.

El modo de fallo del paquete perdido

Los síntomas son aburridos y caros:

  • Teatro de CRC. Se parsean frames, los checksums son opcionales y un bit invertido se convierte en una temperatura plausible.
  • RAM como buffer. El gateway guarda telemetría no sincronizada en memoria volátil. Un parpadeo de alimentación; los datos del turno nunca existieron.
  • Reconexión ingenua. Vuelve la red de planta. Doscientos nodos reintentan en el mismo milisegundo. El servicio de ingestión es el corte.
  • POSTs no idempotentes. Un replay tras un timeout cuenta dos veces volumen, energía o ciclos de lubricación. Finanzas se entera antes que ingeniería.

Lo aprendí primero en Smart Lub para Vulcano Lubricación — un dispositivo de telemetría RS485 que tenía que sobrevivir a una fábrica y luego a un catálogo comercial. Lo volví a aprender en charge points OCPP 1.6-J, donde un WebSocket caído es un problema de medición y de comando remoto, no un spinner en un teléfono.

Tres principios que sobreviven al piso de planta

Todo lo demás es un detalle de implementación de tres reglas.

  1. Toma en serio la capa física. La señalización diferencial rechaza ruido de modo común; no inventa integridad. CRC (o checksum del protocolo) en cada frame, timeouts que resetean UARTs trabados, un watchdog de hardware que no quiere a nadie.
  2. Durabilidad antes que elegancia. Los frames no sincronizados viven en EEPROM, flash o una SD industrial con plan de desgaste. La RAM es una cache, no un log.
  3. El replay es el happy path. Sequence IDs, upserts idempotentes y backoff con jitter. La nube debe asumir que cada paquete llegará dos veces, tarde o en un burst después de un apagón.

El sistema en capas

Nombra las capas para que un ingeniero de firmware y uno de backend puedan discutir las mismas cajas.

Física y enlace

RS485 es un par diferencial con polaridad, terminación y bias que en campo se cablearán mal. OCPP 1.6-J es JSON sobre un WebSocket TLS persistente con una máquina de estados a la que no le importan tus hábitos REST. Ambos son enlaces que se caen. Ninguno es “HTTP con headers extra”.

Gateway de edge

Microcontrolador o caja Linux pequeña: decodificar, verificar, bufferizar, publicar. En Smart Lub eso significó frames estilo Modbus con CRC, Ethernet o Wi-Fi como camino northbound, y storage local para que el reboot de un switch de planta no fuera un evento de pérdida de datos. En cargadores significó mantener honesta la sesión OCPP mientras los ticks de medición seguían en local.

Ingestión y producto

Cloud Run (o equivalente), una verdad con forma de PostgreSQL y una superficie de ops en Flutter o web. El trabajo primario de la API es la deduplicación. La visualización es un privilegio que ganas cuando el ledger ya es aburrido.

Los comandos southbound — parada remota, empujón de firmware, start transaction — necesitan sus propios timeouts y acknowledgements. Un handler HTTP trabado no debe detener la ISR de UART. Aquí los tests de arquitectura son tests de integración con la NIC muerta, no mocks que siempre tienen éxito.

Respeta el ruido, la paridad y el silicio trabado

Los pisos de fábrica y las bahías de carga al aire libre son generadores de EMI con un estacionamiento pegado. RS485 diferencial ayuda. El firmware igual tiene que:

  • Calcular CRC16 (o el checksum del protocolo) en cada frame y descartar fallos sin un “best effort decode”.
  • Acotar lecturas con timeouts de hardware para que un bit de stop ausente no cuelgue el main loop.
  • Alimentar un watchdog que resetee un transceptor trabado en vez de esperar un viaje de camión.

OCPP no es ruido analógico, pero rima: JSON malformado, TCP half-open y un charge point que cree que sigue en una transacción. Trata la validación de schema como CRC. Trata los idle timeouts como timeouts de framing UART.

Ack solo después de durabilidad en ambos lados. Vaciar un buffer local porque el write TCP devolvió es cómo pierdes la ventana del apagón. El sequence ID se limpia cuando la API de ingestión reporta un upsert committed — o cuando un job posterior de reconcile dice que la nube ya lo tiene.

La conectividad intermitente es el modo de operación

En teléfonos, una caída es un spinner. En una línea de lubricación o un cargador, una caída es facturación perdida o un rodamiento seco. Diseña para la partición:

  • Buffer local. Log circular en EEPROM o flash con high-water mark y una estrategia para cuando el log está lleno (descartar lo más viejo vs fail closed — una decisión de producto, no un wrap silencioso).
  • Ingestión idempotente. deviceId + sequenceId único (y para OCPP, las identidades de transacción y meter-value que la spec ya te da). Los replays hacen merge; no anexan un segundo universo.
  • Backoff con jitter. Restaurar la energía de un sitio es un thundering herd con cables Ethernet. Backoff exponencial sin jitter es un self-DoS sincronizado.

OCPP 1.6 es la misma arquitectura vestida de traje

Un CSMS que sostiene conexiones WSS persistentes a charge points es el publicador Ethernet de Smart Lub con una máquina de estados más grande. Los meter values son frames de telemetría. RemoteStartTransaction es un comando southbound con deadline. La conciliación de facturación es el ledger idempotente con consecuencias legales.

El dashboard Flutter no es el sistema. Es un subscriber del estado committed. Si la UI está viva y el camino de ingestión no es durable, has construido un demo que miente rápido.

Log de edge más API idempotente

  • Los apagones se vuelven demora, no pérdida.
  • Los reintentos de backend son seguros por construcción.
  • Ops puede explicar huecos como “aún no acked”, no “tal vez se fue”.
  • El mismo patrón porta de Modbus a OCPP sin una religión nueva.

La fantasía del buffer infinito

  • El flash se desgasta. La EEPROM se llena. Necesitas una política de drop.
  • El clock drift convierte el “event time” en un debate salvo que los dispositivos tengan una historia de sync.
  • La entrega exactly-once es un mito; los efectos exactly-once son una clave de upsert.
  • Los comandos southbound durante una partición necesitan un estado pending visible para el operador.

La literatura de industria sobre IoT suele detenerse en “usa MQTT y QoS 1”. Así obtienes un montón distribuido de mensajes únicos y una base llena de gemelos. Un espacio de secuencia, un log durable y un upsert son la supervisión adulta mínima.

La ventaja full-stack, sin mística

Saber por qué un MAX485 necesita terminación no te hace, en abstracto, mejor desarrollador React. Te hace rechazar APIs que no pueden hacer replay, UIs que tratan “connected” como “true” y firmware que bloquea en HTTP en el camino de recepción. El instinto a nivel de registro es un sesgo hacia trabajo acotado y fallo explícito.

Pros y contras, sin el slideware

Dimensión Lo que ganas Lo que pagas
Integridad Los frames corruptos mueren en el edge. El ledger ve hechos verificados. Descartas datos que no puedes probar. Contadores y alarmas deben mostrar el drop.
Disponibilidad El sensing continúa con un WAN muerto. El replay cierra el hueco. Storage local, desgaste y un job de reconcile que alguien tiene que poseer.
Nube Ingestión horizontal que asume duplicados. La matemática de facturación sigue siendo explicable. Los contratos de schema y secuencia son para siempre. Cambiarlos es un problema de flota.
Operaciones Los dashboards reflejan estado committed; los técnicos debuguean acks, no vibes. Igual mandarás un camión por polaridad, terminación y un RJ45 mojado.
Transferencia Las lecciones de RS485 se transfieren a OCPP, y de vuelta, porque los modos de fallo riman. Los equipos sobre-abstraerán “la plataforma IoT” y publicarán un gateway que no hace nada bien.

Cuándo no hacer esto

  • Enlaces solo de laboratorio. Si el dispositivo nunca sale de un banco y los datos no son dinero ni metal, un script Python y un CSV es honesto.
  • Sin espacio de secuencia. Si no puedes nombrar un evento único, no puedes hacer upsert. No tapes eso con “Kafka lo ordenará”.
  • Firmware cloud-first. Si el loop de muestreo espera HTTPS, has acoplado la física al SLO de otro.
  • Un dashboard como fuente de verdad. WebSockets en vivo que bypassean el ledger discreparán con las facturas. Elige una fuente; que sea la base de datos.

Cierre

La telemetría industrial es un sistema operativo para particiones, vestido de cable serial. CRC, logs no volátiles, replay con jitter y upserts idempotentes son cómo evitas que una fábrica o una red de carga invente datos. También son cómo heredas una nueva clase de trabajo: desgaste de flash, epochs de secuencia y un equipo de plataforma que debe tratar el edge como un kernel.

Usa esta forma cuando la pérdida es un evento de seguridad o de facturación. Sáltala cuando sigues siendo un sensor en un escritorio. Y nunca confundas un dashboard conectado con un sistema durable — el cable sigue haciendo ruido, la energía sigue cayendo y la nube igual tiene que sobrevivir a que le cuenten la misma verdad dos veces.
