When fifty-plus engineers across many squads try to ship a banking app as a classic Flutter monolith, the failure is organizational before it is technical: merge queues stall, CI times explode, and a defect in cards freezes a release that payments never touched.

This article is a field guide for the architecture that fixes that — without pretending Flutter micro-apps are independently deployable like web micro-frontends. They are compile-time modules assembled by an app shell into one store binary. Squads own micro-apps (one domain per package). They never import each other. They integrate through the shell and talk through a capability registry, typed pub/sub, and the router. That distinction drives most of the trade-offs below.

What this is not. It is not a license to split folders “for cleanliness.” If you have fewer than three squads, a well-bounded modular monolith is cheaper. The architecture here exists to let many teams move in parallel without sharing a route table, a pubspec, or a mental model of the entire tree.

The fifty-engineer failure mode

The symptoms are boring and expensive:

  • Merge storms on the global route table, theme, and dependency tree.
  • CI that cannot be localized. A copy change in statements re-runs golden tests for onboarding.
  • State-management drift. One squad standardizes on BLoC for ledgers; another standardizes on Riverpod for forms; neither owns the boundary.
  • A single binary, a single blast radius. Payments cannot ship because cards failed a screenshot test.

Banking makes this worse. You still have one App Store listing, one Google Play listing, often a third store for devices without Google services, a shared RASP surface, and a regulator who does not care that “that screen belongs to another squad.” The architecture has to isolate work, not isolate liability.

Three principles that actually scale

Everything else is an implementation detail of three rules.

  1. Composition over inheritance. Micro-apps and vendor SDKs are assembled by the shell. Nobody subclasses “the bank app.” Deep hierarchies become un-mergeable politics.
  2. Coordinated lifecycle. The shell boots once, registers every micro-app, and calls each package’s bootstrap during startup. Heavy I/O belongs in lazy services, not in blocking init.
  3. No direct micro-app-to-micro-app imports. If payments needs an account carousel, it asks the registry. Compile-time coupling is how Conway’s law turns into a distributed monolith with extra steps.

The layered system

Name the layers so ownership is obvious. Ambiguous names are how “core” becomes a junk drawer.

App shell (composition root)

The only compile target that ships to stores. It registers every micro-app, boots the capability registry, aggregates routes and localization delegates, wires dependency injection, and owns session guards. Product squads do not edit this repository except through a reviewed integration PR. The shell is thin on purpose: orchestration, not business logic.

Micro-apps

One domain per package: payments, accounts, cards, statements, onboarding. Each micro-app exposes guarded and public routes, InteropApi handlers for other packages (registerRequest, registerWidget), localization delegates, injectable dependencies, and a one-time bootstrap hook. Each package also ships an isolated runner (an example/ app) so a squad can hot-reload their world in seconds without assembling the host.

Shared platform kit

Design system, networking abstractions, storage, analytics facades, observability, fraud signals, and wrappers around vendor SDKs. Squads consume interfaces. The platform team swaps Google versus Huawei implementations, or a new crash reporter, without a fifty-file refactor.

Squad-only plugins

A few capabilities are not shared: NFC contactless, liveness for KYC, a proprietary card-scan camera. Those live in packages owned by the squad that needs them. They are the exception that proves the BOM rule below.

Enforce the dotted lines with analyzer plugins or a simple CI grep over import URIs. Social agreements rot in week three. Architecture tests do not.

Integrating a micro-app into the app shell

A micro-app does not “plug in” by adding a folder under lib/features. It integrates through a container contract the shell understands. Think of it as a manifest the platform team registers once per package.

Each micro-app implements an abstract container that declares:

  • A unique name — used in logs, crash attributes, and the interop catalog.
  • Guarded routes — screens that require an authenticated session.
  • Public routes — onboarding, legal, password recovery.
  • InteropApi — request and widget routes other packages call via makeRequest and getWidget.
  • Declarative action parsers — optional handlers for push payloads and server-driven navigation JSON.
  • Localization delegates — the shell merges them into MaterialApp.
  • Injectable dependencies — repositories and use cases registered during bootstrap.
  • bootstrap() — one-time init: listeners, remote-config subscriptions, analytics setup.

The integration checklist for the platform team is short and non-negotiable:

  1. Import the micro-app container in the shell project.
  2. Add it to the shell’s micro-app list (order matters if routes could collide — platform resolves conflicts).
  3. Pass module configuration (API base URLs, feature flags) through constructor injection, not globals.
  4. Verify guarded routes sit behind the shell’s auth redirect.
  5. Smoke-test deep links that target the new routes.

Startup tax is real. Bootstrapping every micro-app at launch costs Dart isolate work, DI graphs, and native plugin registration. Mitigate with lazy service construction inside bootstrap, not by skipping registration. A missing interop route at runtime is worse than a few extra milliseconds at cold start.

Four ways micro-apps talk

Low coupling is not “no communication.” Banking UIs are mosaics: the home screen is a host of widgets owned by five squads. You need a small, named set of channels — and you need to refuse a fifth.

1. Router hand-off

Delegate an entire flow — login, KYC, device binding — and pass a return location via a query parameter (for example re_direct=/home). The callee pops with a result. This is the right tool when the user should leave your micro-app. Pros: obvious back stack, easy to deep-link. Cons: you cannot embed a slice of that flow on a dashboard.

2. Interop widgets — getWidget

The owner registers a handler with interop.registerWidget('/accounts/balance-card', …). Callers embed UI with interop.getWidget(route, params). The owner builds the widget with its own state and use cases. The home squad never imports accounts. Pros: true UI reuse across squads. Cons: layout surprises, async holes while the widget loads, and a home screen that fails in pieces instead of as a unit. Always pass an error placeholder.

3. Interop requests — makeRequest

The owner registers a handler with interop.registerRequest('/profile/device-info', …). Callers fetch data with interop.makeRequest(route, params) — synchronous-looking request/response for device info, biometric availability, a sanitized profile. Parameters are a dictionary; the contract lives in the interop catalog, not in a shared model package that everyone depends on. Pros: no UI entanglement. Cons: untyped maps, runtime “route not found,” and the temptation to smuggle DTOs as JSON strings forever. Publish the catalog. Version the routes. Reject unknown required keys.

How InteropApi works

Think of InteropApi as internal HTTP: each micro-app publishes routes at bootstrap; callers address them by path. The shell owns a single InteropRegistry that dispatches to the owning package. No caller imports the owner — only the route string and the catalog contract.

Registration is owner-side (registerRequest, registerWidget). Invocation is caller-side (makeRequest, getWidget). The registry resolves the route, validates required parameters against the catalog, and forwards to the handler. If the route is missing or params are wrong, fail fast with a typed error — not a null widget on the home screen.

4. Typed pub/sub

Session established, session dropped, uncaught error, remote-config bag changed, accounts list refreshed. These are facts about the world, not requests. The platform team owns the channel types. Squads must cancel subscriptions when a widget disposes. Pros: many listeners, no import cycle. Cons: a global bus is how hidden coupling returns. If you need a request/response, it is not an event.

Registry and bus

  • Squads ship without waiting on each other’s source.
  • You can mock interop routes in the isolated runner.
  • Unique interop routes prevent silent collisions.
  • Performance traces can tag a destination route.

The distributed monolith

  • Failures move from compile time to production.
  • Call graphs vanish from “find references.”
  • A renamed route is a silent home-screen hole.
  • Overusing the bus recreates spaghetti with extra hops.

Industry writing on Flutter super-apps often stops at “use an event bus.” That is how you get a distributed monolith: every feature depends on a singleton, none of the edges are typed, and onboarding a new engineer means grepping strings. A registry with required parameters, status codes, and a human-readable catalog is the minimum adult supervision.

Inside a micro-app

The folder template is not bureaucracy. It is how someone from another squad can open a PR on Friday without a tour. A package that cannot be navigated in ten minutes will be copied, not extended.

micro_app/
  l10n/
  lib/src/
    interop/
      requests/          # registerRequest handlers — data routes
      widgets/           # registerWidget handlers — view routes
    config/
      dependency_injection/
      network/           # api_endpoints.dart — no magic URLs in datasources
      remote_config/
      storage/
      analytics/
    commons/             # helpers local to this micro-app
    features/
      transfer/
        data/
          models/
          data_sources/
          repositories/
        domain/
          entities/
          repositories/
          use_cases/
        presentation/
          providers/       # or blocs — presentation state only
          screens/
          widgets/
  test/                  # mirrors lib/
  example/               # isolated runner — the squad's daily driver

Presentation vs domain wiring

Presentation state (Riverpod, BLoC, or similar) lives under features/*/presentation. Domain and data layers are constructed through the injector the shell provides — not through ad-hoc ProviderContainer() inside interop handlers. Two DI systems in one package is how tests flake and memory leaks hide in registerRequest callbacks.

InteropApi lives at the package edge

registerRequest handlers call use cases. registerWidget handlers return widgets built with the owner’s providers. Shared widgets used only by interop sit in features/shared. The interop layer is the public API of your micro-app to the rest of the bank — document every route in the catalog.

Config is code, not folklore

  • No raw strings in UI. Localization files are part of the package contract; the shell aggregates delegates.
  • Enumerate endpoints, remote-config keys, storage keys, and analytics events in config files. Searching the repo for a magic string during an incident is not a strategy.
  • Immutable models. Code-generated unions for states beat “a nullable entity plus three booleans.”
  • Navigation from the notifier, not the widget, using the injected router abstraction the shell exposes.

The isolated runner is the onboarding product. A new engineer should clone one repository, run one command, and see transfers — not wait for the host’s flavor matrix, signing, and fifty other packages to resolve.

The platform operating system

At this scale the platform team is not “the people who do tickets nobody wants.” They are the kernel.

A dependency bill of materials

Pub cannot put two versions of the same package into one binary. If payments pins http ^0.13 and cards pins http ^1.1, the host does not build. The fix is a BOM package: micro-apps depend on the BOM, not on pub.dev, except for truly encapsulated squad plugins. Dart workspaces (SDK 3.6+) and Melos are the ecosystem’s version of the same idea — one resolution, one lockfile. A banking org still wants the BOM as a policy artifact: upgrading Dio is a platform RFC, not a drive-by in a squad sprint.

Wrappers, not SDKs in feature code

Analytics, crash reporting, remote config, geolocation, and secure storage all have two lives on Android: Google Mobile Services and Huawei Mobile Services. Feature code that imports a vendor plugin will be rewritten twice. Wrap them. The wrapper is also where you attach a microapp attribute to every event and crash, which is the only way a unified dashboard pages the right squad.

CI the squads cannot fork

Reusable workflows: format, analyzer (including a strict ruleset such as Very Good Analysis minus noise), unit tests, coverage upload, SAST. Squads do not own the workflow files. If they need a new job, they propose it to platform. Path-filtered CI on the host still runs the world; path-filtered CI on a micro-app repository must be fast enough that waiting feels rude — under four minutes is a reasonable target.

A release train, not a heroics calendar

Independent packages still leave the store as one artifact. A two-week train — branch cut, signed multi-store builds, staged rollout — is the integration cadence. The train is an operating model, not an architecture. Treat it as such; do not invent a second composition root to avoid talking to QA.

Banking extras the textbooks skip

Deep links and declarative actions

Campaign tools and push notifications send JSON: “open payment for amount X.” Each micro-app registers parsers by actionType; the shell aggregates them. Deep links target routes owned by specific micro-apps — the shell’s router must know which package owns which path. Parsers and deep links must run through the same auth guards as typed routes. This is how you ship a seasonal flow without waiting for store review — and how you accidentally ship a navigation gadget with no authentication if guards are skipped.

Unified observability

Stamp microapp (and feature, where useful) on every analytics event and crash report. Otherwise you will page the wrong squad at 2 a.m. One project, one taxonomy, required ownership attributes. Migration from legacy dashboards is a program, not a ticket.

Compile-time modules still bloat the binary

Tree-shaking helps. It does not delete a native KYC SDK that most users will never open. Measure with flutter build --analyze-size, ship Android App Bundles, and be vicious about squad-only plugins. Flutter is not a micro-frontend runtime; you cannot download a feature graph later.

PCI and RASP are shell concerns

Card data should never enter a squad’s Dart heap if a tokenizer can stop it at the SDK. Root detection, hooking, and debugger checks belong in the shell, uniformly. A micro-app that “implements its own jailbreak check” is a finding, not a feature.

Team topology

Conway’s law is not a metaphor here. The repo graph will copy the org chart. Design the org chart on purpose.

One micro-app, one owning squad. Shared packages have a named steward, not “whoever touched it last.” The platform team is a bottleneck by design: BOM upgrades, shell integration, new broadcast types, CI templates. That bottleneck is cheaper than twelve versions of Dio. Staff it. If platform is two people supporting twelve squads, you do not have a platform. You have a queue of blocked sprints.

Integration into the shell is a checklist, not folklore: container class, unique name, routes, interop handlers, parsers, localization, DI, bootstrap, remote-config keys, deep links, crash attributes, analytics events. Until that checklist is boring, every new package will be a production incident.

Pros and cons, without the slideware

Dimension What you gain What you pay
Team velocity Parallel work, isolated runners, smaller PRs, onboarding in days not weeks. Integration PRs into the shell still serialize at the train. Platform becomes a queue.
Coupling No compile-time cycles between micro-apps. Clear ownership per domain. Runtime coupling via string routes. Catalogs and contract tests are mandatory, not optional.
Product One cohesive app, one identity, one store listing, shared design system. Shared process, shared RASP surface, shared binary size. A native crash in any SDK affects everyone.
Quality Micro-app CI is fast. You can golden-test a flow without booting the bank. End-to-end still needs the shell. Interop holes appear only when graphs are composed.
Governance BOM, wrappers, and locked workflows stop dependency roulette. Squads feel constrained. Shadow pubspec entries will appear unless review is sharp.
Operations Unified analytics and crashes with a micro-app dimension. Building the catalog and keeping it current is ongoing platform work.

The architecture also fails in characteristic ways. Bootstrap-everything inflates startup. getWidget calls turn the home screen into a distributed system. A “shared” package that secretly depends on one squad’s domain infects everyone. Lifecycle leaks — a socket or stream subscription that survives widget disposal — become data bugs in a bank, not academic edge cases.

When not to do this

  • Fewer than three squads. You will spend more time on the shell than on the product. Use packages for the design system and stop.
  • No platform team. Without stewards for CI, BOM, and the interop catalog, this design decays into a federation of incompatible Flutter apps that still have to compile together.
  • A need for true independent deployability. Flutter will not give you that in the store. If you need to ship cards without a binary, you are talking about server-driven UI or a web surface, not another Dart package.
  • Micro-apps as folders, not packages. If everything still lives in one repo with no isolated runner and no import bans, you have renamed a monolith, not modularized it.

Closing

Large-scale Flutter banking architecture is an operating system for teams, wearing a mobile UI. The app shell, the micro-app, the capability registry, and the BOM are how you keep fifty engineers from sharing a file. They are also how you inherit a new class of failure: stringly-typed integration, a heavier binary, and a platform team that must be staffed like a kernel team.

Use the shape when the org is already too big for one squad and one route table. Skip it when you are still one team with ambition. And never confuse independently developable micro-apps with independently shippable apps — the store still gets one artifact, and the regulator still sees one bank.
